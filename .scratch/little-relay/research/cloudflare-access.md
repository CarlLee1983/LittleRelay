# Cloudflare Access for LittleRelay owner login

Checked 2026-10-05 against Cloudflare's official documentation. **Facts** below describe Cloudflare behavior; **suggestions** are design choices for LittleRelay.

## Cost and identity

- **Fact:** Cloudflare's Zero Trust Free plan is $0 with a **50-user limit**. Its listed standard log retention is up to 24 hours, support is community forums/Discord, and paid pay-as-you-go is listed at $7/user/month with no user limit. This is separate from any Workers, Pages, or storage charges. [Cloudflare Zero Trust pricing](https://www.cloudflare.com/plans/zero-trust-services/)
- **Fact:** New Zero Trust organizations default to the Cloudflare identity provider. One-time PIN (OTP) is optional and must now be added explicitly. An approved email receives a single-use code that expires after 10 minutes; a denied email does not receive one, though the page still says it was sent. OTP can coexist with another IdP. [Identity providers](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/), [One-time PIN login](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/)
- **Fact:** An Access application is deny-by-default and needs an Allow policy. Allowing the `One-time PIN` login method alone without a specific email/domain Include rule can let any email address in. [Self-hosted public app setup](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/), [Common policies](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/common-policies/)
- **Suggestion:** For the owner, use one exact, recoverable owner email in an Allow policy and either Cloudflare account sign-in or OTP. Do not use an email-domain-wide rule for owner privileges. Keep buyer eligibility and LINE-account admin authorization in the application, separate from Access identity. If LINE admins do not themselves authenticate through Access, an Access rule covering the *whole* back office would block them: scope Access to owner-only routes or give those admins their own Access identities and policies. This follows Access's per-request gate and path scoping. [Application paths](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/), [Self-hosted public app setup](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/)

## Route protection and server-side identity

- **Fact:** Create a Self-hosted and private application with a public hostname under Zero Trust > Access controls > Applications, attach the policy, select allowed login methods, and set session duration. A Cloudflare-managed active domain is required (full or partial CNAME setup). Access can target a hostname or paths; a more-specific path application takes precedence over a parent and does **not** inherit its policy. `/owner/*` does not cover `/owner` itself. [Self-hosted public app setup](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/), [Application paths](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/)
- **Fact:** For Workers, hostname/path Access protects only matching URLs; Worker-level Access protects the Worker across its routes, Custom Domains, `workers.dev`, and previews. Path/hostname rules have precedence over Worker-level rules. A mixed public buyer and private owner Worker therefore needs precise path rules and route auditing, including alternate hostnames. [Access for Workers](https://developers.cloudflare.com/workers/configuration/cloudflare-access/)
- **Fact:** For Pages, the Access Pages Plugin can validate assertions in Pages Functions using the team `domain` and application `aud`. Pages also has a `*.pages.dev` production URL and preview URLs; protecting a custom domain alone does not remove those alternate paths. Cloudflare documents separate Access/redirect handling for the Pages URLs and a known-issues procedure when custom domains and Pages Access coexist. [Pages Access Plugin](https://developers.cloudflare.com/pages/functions/plugins/cloudflare-access/), [Pages custom domains](https://developers.cloudflare.com/pages/configuration/custom-domains/), [Pages known issues](https://developers.cloudflare.com/pages/platform/known-issues/)
- **Fact:** Cloudflare sends an application JWT in `Cf-Access-Jwt-Assertion`. A raw header or decoded claim is not proof of identity; verify its signature with the team's `/cdn-cgi/access/certs` keys plus issuer, audience, and expiry. Keys normally rotate every six weeks, with the prior key valid seven days; fetch the JWKS dynamically. The signed claim set includes `email`, `sub`, `aud`, `iss`, and `type`; `sub` changes if a user is removed and re-added or changes Zero Trust organization. [Validate JWTs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/), [Application token](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/)
- **Fact:** A directly Access-authenticated Worker can read trusted identity via `ctx.access.getIdentity()` without parsing a JWT. `ctx.access` is undefined when Access has not authenticated that invocation. It does not propagate through service bindings, and a Worker using Static Assets does not receive it from the internal router. [Access for Workers](https://developers.cloudflare.com/workers/configuration/cloudflare-access/)
- **Suggestion:** On each owner-only handler, fail closed if Access identity is absent or invalid, then map verified owner identity to LittleRelay's owner role. On LINE-admin handlers, verify LINE authentication and the store's admin grant independently. Never grant a role from unverified `Cf-Access-*` headers. For a Pages Function use its Access plugin or explicit JWT verification; for a direct Worker prefer `ctx.access` where its documented limitations permit it. Keep authorization checks on the server endpoints, not merely on the UI route. [Pages Access Plugin](https://developers.cloudflare.com/pages/functions/plugins/cloudflare-access/), [Access for Workers](https://developers.cloudflare.com/workers/configuration/cloudflare-access/), [Validate JWTs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)

## Development, recovery, and per-store deployment

- **Fact:** `wrangler dev` runs Worker code locally with simulated bindings by default. Access identity can be simulated locally through `access.dev` for `ctx.access`, including an unauthenticated case by omitting that block. Connecting to Access-protected remote bindings invokes an interactive Access login for human development or requires a service token and Service Auth policy for non-interactive CI. [Local development](https://developers.cloudflare.com/workers/local-development/), [Access for Workers](https://developers.cloudflare.com/workers/configuration/cloudflare-access/)
- **Suggestion:** Test both denied and allowed owner requests, wrong-store identity, missing/forged JWT, and public buyer paths locally. Also perform a deployed smoke check of every production/preview/custom hostname because local Access simulation does not exercise edge policy matching. [Access for Workers](https://developers.cloudflare.com/workers/configuration/cloudflare-access/), [Application paths](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/)
- **Fact:** A Cloudflare dashboard administrator can edit an Access policy; changes take effect for associated apps. This is the recovery path if only the *application* policy or owner email is lost and dashboard access remains. Dashboard account recovery is distinct: Cloudflare recommends backup codes for lost 2FA, and documents a verified-device/manual recovery process when those are gone. Access independent-MFA authenticators can be deleted by an administrator to let the user re-enroll. [Policy management](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/policy-management/), [2FA](https://developers.cloudflare.com/fundamentals/user-profiles/2fa/), [Account recovery](https://developers.cloudflare.com/fundamentals/user-profiles/account-recovery/), [Independent MFA](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/independent-mfa/)
- **Fact:** An already-issued Access application token remains usable for its configured lifetime. Access supports revoking existing tokens for one application or a user's sessions across applications; the old identity must also be removed from the applicable policy or identity provider to prevent a fresh login. [Session management](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/)
- **Suggestion:** Keep the Cloudflare dashboard owner account, a second authorized dashboard administrator where feasible, backup codes, and the Access policy configuration recoverable outside the app. Do not create an unauthenticated emergency owner URL; restore the approved email/policy through the dashboard. [Cloudflare account security guidance](https://developers.cloudflare.com/changelog/post/2025-10-07-recovery-codes/), [Policy management](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/policy-management/)
- **Suggestion:** For independent store deployments, give each store's owner route its own hostname/path Access application, exact owner Allow policy, and audience value; bind the store's owner role to that deployment's verified identity. Audit every store's alternate `workers.dev`/Pages/preview endpoint. The Free plan's 50-user limit is a plan constraint, so confirm actual account/user accounting and expected owner/admin count before treating per-store cost as zero. [Pricing](https://www.cloudflare.com/plans/zero-trust-services/), [Access for Workers](https://developers.cloudflare.com/workers/configuration/cloudflare-access/), [Pages custom domains](https://developers.cloudflare.com/pages/configuration/custom-domains/)
