# 定義單件商品的結帳一致性與失敗處理

Type: grilling
Label: wayfinder:grilling
Status: resolved
Blocked by: 01, 04, 05

## Question

兩位核准顧客同時購買同一件衣服、同一顧客重送請求、購物車內部分商品已售出，或資料服務達到免費額度時，系統如何保證不超賣、不產生半成品訂單，並清楚告知顧客？顧客購買資格在結帳同時被撤銷時，如何與整張訂單的原子保留一同檢查？每張訂單的確切截止時間與付款回報、系統逾期釋放、另一人結帳同時發生時，如何原子地判定先後？定義整張訂單的保留與釋放、不重複成單、購物車過期內容及可驗證的不變條件。

另須驗證：成單前準備各訂單專屬 R2 私有照片副本，與 D1 成單交易所核對的照片版本一致；R2 準備或 D1 交易失敗時，不能留下半張訂單。涵蓋程序中斷、回應逾時與 D1 結果未知的案例：孤兒副本須可被持續找出並清理，但不得刪除已成單訂單引用的副本。

同時驗證本機商品發布與結帳保留交錯時，兩者都檢查並推進同一商品版本；不能讓過時預覽改寫保留中的商品內容或讓訂單快照引用錯誤照片版本。

## Comments

- 店家確認：任一商品失效或內容變更時整單不成立；保留可買的購物車項目、標示失效或變動處，顧客重新確認後再送單。逾時先查同次結果，重試不得重複成單。
- 顧客資格撤銷與結帳以 D1 先完成的動作為準；訂單先成立則保留舊單。付款回報以資料庫判定時刻為準，嚴格早於截止才有效，等於截止即逾期。舊送單嘗試不能在訂單逾期後自動重建新單。
- 逾期後仍可回報已轉帳供管理員人工處理，不恢復保留。服務失敗時保留購物車並查原結果。每單不設店規件數上限；極端大單若超出實測安全能力，明確提示拆單。正常服務下公開到期標示目標約 5 分鐘內更新，交易判定即時。
- 店家已確認本票整體規格。

## Answer

### 整單保留的不變條件

- 購物車不保留庫存。伺服器只接受經 LINE 驗證、在 D1 當下仍具購買資格的顧客送單；每張訂單的商品 ID 不可重複，且每件衣服同時最多只能屬於一張有效保留訂單。商品須公開、可售，並與顧客確認的價格、內容及整組照片版本一致。任一條件不符，**沒有訂單、沒有任何部分保留**。
- 為每次送單建立可查的「送單嘗試」，以顧客身分與一次性操作鍵綁定固定購物車內容、各商品預期版本及照片副本，並包含顧客確認的交付政策（啟用方式、品牌、服務範圍與運費）及付款指示版本。相同鍵和相同內容的重試，回傳原嘗試或已成立的同一張訂單；相同鍵若帶不同內容則拒絕。訂單已逾期後重送舊鍵，只回傳已逾期結果；顧客須刷新購物車並明確發起新嘗試，不會偷偷重新保留商品。
- 成單前把每件商品當時的主實拍、細節照及 AI 展示照，按此嘗試的固定鍵複製成該訂單專屬的私有 R2 副本，逐一驗證可讀且版本相符；任一副本失敗就不成單。照片準備可分段進行，D1 中的嘗試記錄與副本鍵須可在中斷後找回。R2 與 D1 沒有共同交易，故照片準備成功本身**不代表**訂單成立。[Cloudflare R2 一致性](https://developers.cloudflare.com/r2/reference/consistency/)
- 最終由**一筆 D1 交易**同時確認目前顧客資格、送單嘗試、所有商品公開／可售狀態與版本，以及顧客確認的交付政策、選定品牌／門市是否仍合規與付款指示版本；建立訂單及每件商品快照，將全部商品保留給該訂單，記錄總件數與操作結果。商品、訂單及嘗試的唯一性／數量條件須由資料庫約束或交易內明確斷言強制；任何一項失敗都須在交易內產生錯誤並回滾全部變更。可行候選是批次最後寫入一筆帶 `NOT NULL CHECK (passed = 1)` 的驗證紀錄，`passed` 由當前資格、預期與實際明細數、每件保留歸屬及商品版本計算；任一不符便寫入 `0`，讓 SQL 約束在批次內報錯。`batch()` 在 SQL 陳述式報錯時可回滾，但條件更新影響零列不會自行報錯，不能等批次成功後才檢查受影響列數。實作需在真實 D1 驗證此斷言與並發案例，不將候選寫法視為已證實。[Cloudflare D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)、[D1 回傳資料](https://developers.cloudflare.com/d1/worker-api/return-object/)
- 訂單金額與名稱、價格、照片版本均取自提交交易看到的 D1 內容並成為商品快照；付款與運費欄位依[人工付款與寄送規則](10-manual-payment-shipping.md)固定。結帳及本機發布都檢查並推進同一商品版本。發布先完成則過時購物車整單失敗；結帳先完成則商品進入保留，既定規則禁止本機修改保留中內容。[本地上架工作流](06-local-publishing.md)

### 並發、截止時間與購物車

- 兩位顧客同時搶同一件，只有先通過 D1 交易者成單；另一人看到該商品已不可購買。多件商品只要一件被保留、售出、暫停或撤下，或價格／照片版本變了，整單退回重新確認，不自動替換新價格或照片。購物車保留其餘可買項目、標示失效與變動；重送須使用新嘗試。
- 管理員撤銷資格與顧客結帳的競爭，也以 D1 交易先後判定：撤銷先完成，結帳失敗並清空購物車；結帳先完成，訂單保留，之後撤銷只禁止新購買，顧客仍能查看舊單與回報付款。[顧客核准與管理員權限](04-buyer-approval.md)
- 訂單在提交交易中寫入資料庫判定的建立時刻及確切截止時間；每店 1／2／3 天，預設 2 天，設定變更只影響新訂單。每筆付款回報、延長、取消與到期交易各在 D1 擷取**單一 UTC 判定時刻**，用一致的整數時間精度記錄與比較，不在批次的各 SQL 陳述式重新取現在時間。付款回報只在訂單仍待付款且判定時刻 **早於**截止時轉為「付款待核對」並暫停到期；在截止當刻或之後不轉換。逾期處理只在仍待付款且時間已到時，原子地將整張訂單標為已逾期，釋放仍由該訂單占用的全部商品。管理員延長期限亦須在舊期限前完成；誰先在 D1 成功提交，另一方須重新檢查狀態，不能以顧客裝置時間或按鈕時間倒推優先權。[SQLite 日期時間函式](https://www.sqlite.org/lang_datefunc.html)
- 管理員若在截止前發現可歸屬該單的部分或待核入帳，須在**同一筆 D1 交易**中記錄該銀行帳目並把訂單從「待付款」轉為「付款待核對」，暫停自動到期；若截止時間已到，即使排程未清理，也只能記為逾期款項。到期交易只可結束仍為「待付款」且沒有期限內已記錄待核入帳的訂單。兩個交易競爭時依 D1 先提交且符合截止時刻的結果判定，不能讓已記錄部分款的商品被釋出，也不能靠延遲排程復活過期訂單。[人工對帳規則](10-manual-payment-shipping.md)
- 管理員取消未收款訂單時，也要在同一 D1 交易中結束整張訂單並釋放仍由該訂單占用的每件商品；若歸屬或件數不符，整筆操作須失敗並待人工處理。釋出保留只改庫存歸屬，不改商品的「暫停販售／永久撤下」可見性。已收款取消仍按退款流程保持不可購買，不能提早釋出。[商品與訂單生命週期](01-order-lifecycle.md)
- 到期清理由定時工作約每 5 分鐘處理，正常服務下公開標示以此為更新目標；公開快取或排程延遲不能改變交易判定。公開讀取可依 D1 的截止時間推算目前有效可售狀態，不因每次瀏覽而寫入到期結果；結帳與付款回報遇到已過期但尚未清理的保留，須先以 D1 交易結束／核對舊訂單，再依更新後狀態決定結果。不得因排程尚未執行而接受逾期回報或讓未結束的保留產生兩張有效訂單。D1 不可用時無法保證按秒釋出，恢復後補處理，不憑快取擅自賣出。[Cloudflare Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)
- 逾期顧客仍可送出「已轉帳但逾期」訊息供管理員查核；此訊息不改訂單為付款待核對、不恢復商品保留，也不搶回已被別人買走的衣服。退款或重新建立新單由[人工付款與寄送規則](10-manual-payment-shipping.md)決定。[商品與訂單生命週期](01-order-lifecycle.md)

### 失敗、重試與驗收

- 網路逾時或 D1 回應不明時，以原操作鍵查權威 D1 結果；仍不明則顯示「尚未確認成單」，保留購物車，不另產生新鍵或新單。確認失敗後才可用同一嘗試安全重試，或在商品重新確認後建立新嘗試。D1／R2 額度或服務失敗時不宣稱成單，也不以靜態快取判庫存。[D1 免費額度](https://developers.cloudflare.com/d1/platform/pricing/)
- 過期且未成單的嘗試，須先在 D1 原子標記為不可再提交，再查沒有訂單引用其私有照片副本，方可清理；晚到的照片寫入須由再次掃描發現。結果不明或 D1 不可用時暫不刪照片。已成立訂單的私有副本依[儲存邊界](05-data-image-boundary.md)在訂單結束 30 天後清除；進行中的售後案件依[人工付款與寄送規則](10-manual-payment-shipping.md)暫緩，絕不能被孤兒掃除誤刪。
- 已確定失敗的嘗試紀錄只保留 30 天；清理後的舊送單憑證也必須因自身期限失效，不能因 D1 已無舊鍵而重新成單。提交憑證過期只阻止新提交；若原嘗試已成單，登入的原顧客仍可查回同一訂單，即使回應遺失跨過憑證期限。已成立訂單與結果查詢依[顧客資料生命週期](09-customer-data.md)保留，不把失敗紀錄期限套到已成立訂單。
- 不設每單固定件數上限；照片準備可分段，最終提交須在 Cloudflare 單次請求與 D1 限制內安全完成。若極端大單超出實測可支援範圍，送單前明確要求拆單，不能只成立部分商品。實作須量測並驗證上限，避免 D1 Free 每次 Worker 呼叫的查詢限制。[Cloudflare D1 限制](https://developers.cloudflare.com/d1/platform/limits/)
- 驗收至少覆蓋：兩人同搶單件、多件中一件失效、同鍵重送與改內容、照片複製失敗及版本被換、結帳對上發布／資格撤銷、付款回報對上到期／延長、截止時間相等與交易橫跨截止點、未收款多件整單取消對上到期／新顧客結帳、暫停或永久撤下商品釋出後仍隱藏、排程落後、D1 額度耗盡、R2 寫入中斷、D1 已提交但回應遺失、清理遇到晚到照片。每例檢查單一 UTC 判定時刻、訂單數、整單保留、公開可見性、購物車提示及私有照片是否被誤刪；批次失敗的零列斷言須在真實 D1 證明會回滾。
