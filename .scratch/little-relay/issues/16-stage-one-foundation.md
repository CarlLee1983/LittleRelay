# 建立第一階段商店基礎與身分權限

Type: task
Label: ready-for-agent
Status: open
Blocked by: 11

## Problem Statement

目前只有可交接的產品與營運規格，尚無應用程式、D1 遷移、測試環境或可驗證的登入與授權邊界。複製商店的家庭無法建立彼此隔離的公開商店與店主入口，也無法安全地辨認待核准顧客、店主及管理員。若先加入商品、結帳或後台功能，舊 session、錯誤主機或未驗證的身分資料可能成為繞過權限的入口。

## Solution

交付可在隔離測試環境運作的每店基礎：獨立的公開商店與店主 Worker、每店設定與可重跑的 D1 遷移、LINE 顧客登入、Cloudflare Access 店主驗證、店主授予及撤銷 LINE 管理員權限，以及在 D1 提交時重新檢查當前身分與角色的共同交易邊界。首次 LINE 登入只建立待核准顧客和申請編號。以真實測試 D1 及兩個 Worker 的 HTTP 入口驗證身分、主機隔離、撤權競爭與失敗封閉；正式營運寫入須等下一階段的備份與暫停閘驗收完成才開放。

## User Stories

1. 身為複製商店的店主，我希望使用自己的 Cloudflare 帳號、網域與 LINE channel，以便我的商店與其他家庭完全隔離。
2. 身為店主，我希望正式與測試環境使用不同的 Worker、D1、R2、網域及 LINE channel，以便合成測試資料不進入正式商店。
3. 身為店主，我希望能依操作說明設定非秘密參數與受保護的秘密，以便複製範本時不散布可用憑證。
4. 身為店主，我希望可重跑的 D1 遷移能建立空白商店，以便新店不用複製首店的顧客、角色或訂單資料。
5. 身為店主，我希望知道每個可到達的正式與測試主機，以便確認沒有繞過店主入口保護的網址。
6. 身為匿名訪客，我希望能進入公開商店的基本頁面，以便在沒有 LINE 帳號時仍能看到商店資訊。
7. 身為匿名訪客，我希望不會因瀏覽公開頁而建立顧客紀錄，以便商店只在必要時蒐集資料。
8. 身為準備登入的訪客，我希望先看到該店現行的個資告知，以便知道登入會提供哪些資料與用途。
9. 身為準備登入的訪客，我希望在個資告知無法取得時暫停登入，以便不在資訊不完整時建立帳號。
10. 身為 LINE 使用者，我希望登入請求與回呼可防止偽造及重放，以便別人不能把其 LINE 身分套到我的瀏覽器工作階段。
11. 身為 LINE 使用者，我希望商店只接受本站預期 provider 與 channel 驗證通過的身分，以便其他店或測試 channel 的 token 無法冒用我。
12. 身為首次登入的顧客，我希望成為待核准顧客並取得申請編號，以便透過既有私人聯絡方式請店家核對。
13. 身為再次登入的待核准顧客，我希望看到原申請狀態，以便重複登入不會產生另一個可衝突的身分。
14. 身為待核准顧客，我希望自己的登入身分不自動取得購買或管理權，以便審核流程確實生效。
15. 身為店主，我希望只有通過整個店主 Worker 的 Access 保護及伺服器端 JWT 驗證後才能進入店主功能，以便單靠網址或偽造標頭不能操作商店。
16. 身為店主，我希望首次建立店主身分有明確的受保護程序，以便空白範本不預設任何人擁有權限。
17. 身為店主，我希望店主 API 每次都核對目前 D1 授權，以便撤權或身分更換後的舊 session 不能繼續寫入。
18. 身為店主，我希望能在核對某位已登入 LINE 使用者後授予管理員角色，以便由可信的人處理後續商店工作。
19. 身為店主，我希望能撤銷管理員角色並留下操作者、對象、時間與原因，以便立即阻止其後續特權操作且可追查。
20. 身為管理員，我希望角色與顧客購買資格分開，以便協助店主不會自動成為核准顧客。
21. 身為店主，我希望管理員不能指派或撤銷其他管理員，以便管理權由店主掌握。
22. 身為店主，我希望店主或管理員若另有顧客身分，系統可驗證兩者關聯，以便後續禁止處理自己的資格、付款及退款。
23. 身為店主，我希望撤銷管理員角色與其進行中的特權寫入由 D1 交易先後判定，以便已撤權者不能在舊頁面送出操作並成功提交。
24. 身為店主，我希望 D1 不可用或無法確認角色時特權寫入被拒絕，以便系統不憑 session 或快取猜測權限。
25. 身為店主，我希望公開 Worker 不提供店主專屬路由，且未知 Host 被拒絕，以便預覽或別名網址不能繞過預期入口。
26. 身為店主，我希望管理員授權與撤銷只影響該店的身分，以便同一 LINE 使用者在其他商店不意外取得權限。
27. 身為店主，我希望可用合成資料測試首次登入、授權、撤權、錯誤身分與錯誤主機，以便正式商店啟用前能觀察到每種結果。
28. 身為店主，我希望在備份與暫停閘尚未通過驗收前，正式環境保持營運寫入關閉，以便第一階段測試不被誤當成可營運狀態。

## Implementation Decisions

- 每店有獨立的公開商店 Worker 與店主 Worker；店主 Worker 整站由 Cloudflare Access 保護。兩個 Worker 只綁定該店資源，未知 Host 拒絕，公開 Worker 不載入店主專屬路由。
- 正式商店與隔離測試商店各用自己的主機、Worker、D1、R2 和 LINE channel。正式站停用平台預設及版本預覽入口，部署檢查列舉並實測所有可到達主機。
- 第一階段建立真正會使用的最小資料模型與版本化遷移：商店與環境識別、目前個資告知、經驗證的 LINE 顧客身分與申請狀態、Access 店主身分、LINE 管理員授權、店主與 LINE 顧客身分關聯，以及權限操作紀錄。商品、訂單和邀請碼的詳細結構隨後續功能實作及遷移加入，不預先建立空殼流程。
- 顧客身分以經伺服器驗證的 provider／channel／LINE user ID 對應，顯示名稱只供辨識。登入使用回呼狀態與防重放檢查，伺服器安全換取並驗證 token；不能信任瀏覽器傳入的 LINE ID 或角色。
- 初次 LINE 登入僅建立待核准顧客及申請編號；再次登入使用同一身分與當前申請狀態。只蒐集必要身分資料，不要求頭像、Email 或好友清單。建立帳號前須取得目前個資告知；D1 不可讀時停止新增個資。
- 店主身分由已驗證的 Access JWT 和 D1 當前授權共同決定。首次店主建立須有受保護、可追查且只執行一次的引導程序；範本不含預設店主。Access 失效從該店 Cloudflare 帳號修復，不讓 LINE 管理員升級接管。
- 管理員必須先以 LINE 登入，再由店主核對本人並授權。管理員角色與顧客購買資格彼此獨立；只有店主可授予及撤銷管理員。記錄授權變動的操作者、對象、原因與結果。
- 每筆特權寫入在同一 D1 交易內重新核對商店、經驗證身分、當前角色／授權版本和預期狀態，再提交變更與操作紀錄。條件更新影響零筆必須使整筆操作失敗，不能在交易提交後才當成授權失敗處理。撤權與在途寫入以成功提交的先後決定。
- 店主及管理員若有 LINE 顧客身分，建立可驗證的關聯供後續禁止自我核准、收款及退款；這張票只建立關聯與授權邊界，不開放那些後續業務動作。
- 公開頁使用靜態資產；需要當前身分、個資告知或授權狀態的 API 才讀 D1。秘密留在受限環境設定，不進範本、靜態資產、網址或一般日誌。
- 第一階段只允許隔離測試環境的合成資料寫入。正式營運寫入需經下一階段的帳號外備份、暫停閘與停寫檢查驗收後才啟用；第一階段不得留下可繞過此門檻的正式寫入入口。
- 框架、程式目錄與命令在實作時選定並回填專案指引；這張規格不預設尚不存在的工具鏈。

## Testing Decisions

- 主要測試邊界是兩個 Worker 的 HTTP 入口，加上隔離測試環境的真實 D1。從請求到回應及最終資料狀態驗證外部行為；不以 mock 資料庫或內部函式呼叫宣稱授權、原子性與撤權競爭通過。
- 在同一邊界覆蓋匿名進站、個資告知、合法與錯誤 LINE 身分、首次及重複登入、Access JWT 驗證、店主引導、管理員授予／撤銷、跨店與跨環境隔離、未知 Host，以及 D1 不可用時的拒絕結果。真實 LINE 測試 channel 與 Access 設定另做連線冒煙檢查，不設正式環境的驗證旁路。
- 用管理員授予／撤銷作為第一個實際權限寫入案例，在真實 D1 驗證同時撤權與寫入的提交先後、條件更新零筆時整筆回滾、舊 session 下次特權請求失敗，並檢查操作紀錄與角色狀態一致。
- 列舉正式與測試的自訂網域、`workers.dev`、版本／預覽網址及可能的路由別名，驗證店主入口沒有未受保護的可達路徑。正式營運寫入門檻未滿足時，拒絕結果可由 HTTP 行為及 D1 狀態觀察。
- 好測試描述顧客、店主或管理員可觀察的結果及 D1 權威狀態，不依賴特定框架、函式名稱、SQL 排列或畫面文案。倉庫目前沒有測試程式或相近先例；實作時建立可重跑的測試與文件化命令。

## Out of Scope

- 邀請碼核發與兌換、顧客正式購買資格變更、購物車、商品與照片發布、結帳及訂單狀態。
- 每日帳號外備份、暫停閘、超過 48 小時的停寫、完整還原及營運開放；它們是下一階段的必要門檻。
- 人工付款、退款、交付、售後、資料清理排程、品牌客製化指引與正式部署。
- 線上金流、LINE 推播及多店共用平台。
