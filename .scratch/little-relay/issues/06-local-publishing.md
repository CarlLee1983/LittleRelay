# 定義本地上架、替換照片與下架工作流

Type: grilling
Label: wayfinder:grilling
Status: resolved
Blocked by: 05

## Question

本地處理照片後，如何用可重跑的流程建立商品、發布照片、驗證上架結果、重試失敗、替換素材及下架？訂單完成後哪些內容從公開頁移除，哪些紀錄需留給店家查詢？明確定義管理員手動操作與本地指令的分界。

## Comments

- 店家確認「先預覽檢查、再正式發布」；一次處理多件商品時逐件成功或失敗，提供清楚結果，不要求整批交易。
- 每件商品從一張手機主實拍建立本機草稿，瑕疵／標籤等細節照附加到該商品。Codex 可建議欄位與生成展示照；人工確認所有資料和照片。AI 展示照作封面時須與實拍同頁可見並標示，未生成合格展示照可用實拍上架。
- 暫停販售可由管理員在後台恢復，舊照片網址仍可能可用；永久撤下、確認收款或換照後要清除相應公開照片與快取。保留期間不修改商品內容，重大錯誤由管理員聯絡買家，必要時取消訂單後修正。
- 原圖與處理後本機檔案留在 Git 排除的資料夾，店家自行備份；正式發布前移除照片中的定位資訊、住家細節和孩子可辨識的臉。

## Answer

### 建立草稿與人工預覽

1. 本機以「一件商品一個資料夾及一份商品資料檔」管理。放入一張手機主實拍後建立草稿，分配不隨名稱或檔名變動的商品 ID；後續細節照加入同一商品，不另建商品。原圖、處理後實拍、生成展示照與商品資料都留在 Git 排除的本機資料區，店家自行備份；範本儲存庫只放空白範例。
2. Codex 可依實拍建議標題、價格、尺寸與衣況，但不得把看不出的資訊當事實；尺寸不明時明寫「未標示」。店家逐項確認標題、價格、尺寸、衣況與瑕疵，並檢查主實拍、補充細節照及照片順序。先製作移除定位等中繼資料、裁掉或遮住住家細節與孩子可辨識臉的工作副本；只有該副本可送入可能連線的 AI 生成工具或上傳網站，未處理原圖留在本機。
3. 店家可在本機上架流程中請 Codex 根據已清理的實拍生成較整齊的展示照，只整理背景、光線和擺放，不改衣服的顏色、版型、圖案或瑕疵。人工並排檢查生成照與實拍，不忠實就重做或捨棄；不能把生成結果當作衣況證據。展示照可作封面，頁面同時明示「AI 展示照」與「實物實拍」並提供可開啟的實拍／細節照；沒有合格生成照時，主實拍作封面。品牌風格與可複製的生成指引由[AI agent 客製化指引](14-agent-customization-workflow.md)規定。
4. 正式發布前先產生本機預覽和差異清單，至少核對商品 ID、必要欄位、價格、照片標示與順序、隱私資訊、公開前後變更。草稿與預覽不寫入線上 D1 或 R2；店家確認後才執行發布。

### 逐件發布與重跑

1. 本機發布器先驗證資料與圖片；新商品及仍可售／暫停的商品，把新增或變動的處理後照片直接上傳至該商店的公開 R2，為每個照片版本使用新鍵；未變動照片不重傳。上傳後核對物件可讀，才呼叫受保護的發布介面，由伺服器驗證並更新 D1 的商品內容與照片參照。已售或永久撤下的商品僅能走下述私有暫存重上架流程，不可用一般發布入口新增公開照片。R2 可使用限定 bucket 的憑證；機器呼叫受 Cloudflare Access 保護的入口可使用服務權杖，具體憑證發放由[獨立商店部署決策](08-repeatable-deployment.md)規定。[Cloudflare R2 權杖](https://developers.cloudflare.com/r2/api/tokens/)、[Cloudflare Access 服務權杖](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/)
2. 新商品由伺服器建立初始可售資料；既有商品更新只改文字、價格和照片版本，不能從本機覆寫可售、保留、售出、暫停或撤下狀態。每次發布附預期商品版本及操作 ID；任何內容、庫存或可見性異動都推進該版本，發布介面須在同一 D1 交易中檢查版本及可編輯狀態，並將內容、操作結果與清理待辦一同提交或一同拒絕。若後台操作、結帳保留或另一版內容已先改變，拒絕有衝突的發布並重新預覽。保留中或付款待核對的商品凍結內容；重大錯誤由管理員聯絡買家，必要時取消訂單，確認商品釋出後再修正。條件更新影響零列本身不等於交易失敗，版本衝突須被明確檢出；此競爭案例交由[結帳一致性決策](07-checkout-consistency.md)驗證。[Cloudflare D1 batch 文件](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)
3. 發布器在上傳前於 Git 排除的本機資料區持久記下操作 ID、商品版本與預計上傳鍵；R2 暫存鍵帶操作 ID，讓程序中斷後仍可找回。D1 也記操作結果，讓重新執行能辨認已提交的發布。D1 提交後，重新讀取線上商品及公開頁，確認價格、狀態、實拍與展示照版本，再回報成功。批次逐件處理並列出成功、失敗及待清理項目；同一操作 ID 重跑不得新增重複商品或重傳相同版本。照片上傳失敗時不更新 D1；D1 更新失敗時原商品版本維持可用，未引用的 R2 物件待清理。程序在上傳後中斷或 D1 回應遺失時，先依操作 ID 查 D1 結果與照片參照，不得先刪照片；D1 不可用時保留待查項目並顯示失敗，不宣稱發布成功。過期暫存物件須能定期找出，核對 D1 無引用後才刪除。
4. 換照時先發布並確認新版，再刪除不再被公開商品引用的舊 R2 公開照並按網址清除快取；既有訂單的私有照片副本不變。刪除或清快取失敗要記錄待辦並重試，不能倒退已發布的 D1 內容。刪除 R2 物件後，Cloudflare 快取仍可能暫時供應舊照，須清除快取。[Cloudflare R2 一致性](https://developers.cloudflare.com/r2/reference/consistency/)、[Cloudflare 單檔清快取](https://developers.cloudflare.com/cache/how-to/purge-cache/purge-by-single-file/)

### 後台狀態與公開頁

- **暫停販售／恢復**：店主或管理員在後台改 D1 的可見性，不改訂單或庫存保留狀態。暫停後商品不在公開列表及商品詳情頁；公開 R2 照片仍保留，知道舊照片網址的人可能繼續開啟。恢復時核對商品仍可售或保留中，並保留原訂單狀態。
- **永久撤下**：管理員將商品從公開頁移除，之後刪除公開照片並清快取；商品及既有訂單文字紀錄留在 D1。即使已有保留訂單，也可先撤下公開內容；撤下不會取消訂單或釋放保留，管理員須另依訂單流程聯絡買家並處理。日後重新販售須先在本機準備現況照片、由管理員核對後恢復。
- **售出與退款後重上架**：確認收款時由後台／訂單流程標記售出、移出公開列表並清理公開照片。舊商品頁僅顯示簡短「已售出」，不顯示照片。訂單完成只改訂單狀態，不再次公開或刪改既有紀錄。已收款訂單須完成退款並確認衣服仍可售，才可重新準備上架；本機新照片先經受保護入口放入不可公開的 R2 暫存區，不得讀取或列出其他訂單私有照片。管理員核對衣況及內容後，伺服器把新版本公開並驗證，再於 D1 恢復販售；明確未提交的失敗維持下架並清理未引用的公開副本。此流程沿用操作 ID 與 D1 結果核對規則：若回應遺失或結果不明，先確認 D1 是否已恢復販售，不得宣稱仍下架或刪除已引用的新照。永久撤下後重上架亦採同一暫存與核對流程，不自動復原先前已刪的公開照。[商品與訂單生命週期](01-order-lifecycle.md)、[資料與照片儲存邊界](05-data-image-boundary.md)

公開與私有照片的最終清理期限及訂單快照遵循[資料與照片儲存邊界](05-data-image-boundary.md)；與結帳同時換照的版本競爭交由[結帳一致性決策](07-checkout-consistency.md)驗證。後台操作、確認畫面與待清理提示交由[後台待辦與管理動作](12-admin-workflow.md)細化。
