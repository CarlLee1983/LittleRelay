# 定義邀請碼兌換與資格撤銷的一致性

Type: grilling
Label: wayfinder:grilling
Status: resolved
Blocked by: 04

## Question

同一邀請碼被重送或同時兌換、管理員同時拒絕或撤銷顧客資格、邀請碼剛好到期，或資料服務失敗時，如何保證只有一個結果？定義原子操作須同時檢查經驗證的綁定 LINE 身分、顧客仍為待核准、碼未使用且未過期，再一次性消耗碼並授予購買資格；拒絕或撤銷不能被較晚到達的兌換重新打開。定義失敗提示、重試與可驗證案例。

## Comments

- 店家確認：每位待核准顧客同時最多一組有效碼；補發會作廢舊碼。店主或任何現任管理員可作廢尚未兌換的碼，包含別人核發的碼，並記錄原因。
- 店家確認：有效期從核發的資料庫時間起算完整 168 小時，到期當刻失效。碼只在核發成功時向管理員顯示一次，由管理員透過既有私人聯絡方式傳送；不新增 LINE 推播。
- 店家確認：同一顧客重送已成功兌換的碼時，查回原兌換結果與**目前**資格；之後若已撤銷，不以舊成功結果恢復資格。顧客對錯碼、過期、已用或不屬於自己的碼只看簡短無法使用訊息及自己的申請狀態；後台可查原因。
- 店家確認：核發回應遺失時先查結果；若碼已建立但明文未送達，作廢後補發，不在資料庫保存可找回的明文。核發、兌換、拒絕與撤銷的原子先後由 D1 決定；D1 故障不變更資格。

## Answer

### 核發、作廢與綁定

- 只允許通過 Cloudflare Access 的店主，或經 LINE 驗證且在 D1 **目前仍為管理員**者核發、作廢及補發。伺服器由已驗證的商店與管理員身分決定操作者；目標必須是該店已驗證 LINE provider／channel／user ID 的待核准顧客，不能以顯示名稱或手填 LINE ID 取代。管理員不得為自己的顧客身分核發碼或自行核准。[顧客與管理員權限](04-buyer-approval.md)
- 核發採高熵隨機碼，只保存不可直接兌換的驗證值；碼綁定商店、特定 LINE 身分、**不重用的顧客紀錄識別**與該紀錄的資格世代。核發、補發與作廢各在自己的同一筆 D1 交易中檢查目標仍為待核准；若操作者走 LINE 管理員路徑，交易也檢查其 D1 管理員資格仍有效及不得操作自己的顧客身分。店主走另一條路徑：伺服器先驗證其 Cloudflare Access 身分；若店主另有已關聯的 LINE 顧客身分，也不得對自己的顧客紀錄核發碼，該關聯由[獨立部署票](08-repeatable-deployment.md)建立與驗證。核發還檢查無其他有效碼。交易記錄核發者、核發時間和 `expires_at = issued_at + 168 小時`；提交成功才顯示明文一次。補發或作廢在交易內使舊碼失效並記錄操作者、時間、原因；同一顧客不會同時留下兩組可兌換碼。店主的 Access 憑證與 D1 提交無共同交易，外部撤權／恢復邊界由獨立部署票驗證。管理員私人傳送碼，不把明文放在 URL、一般日誌、分析紀錄或公開頁。
- 核發請求帶一次性操作識別；回應逾時先查 D1 的核發結果，不盲目再建立另一組碼。若核發已成功但明文未送達，後台只顯示「已核發」及必要追查資料，由有權管理員作廢後補發；原明文無法從儲存值還原。D1 無法確認結果時暫停補發，避免兩組碼的歧義。

### 兌換與資格競爭

- 兌換者必須先完成本站 LINE 登入；伺服器從已驗證 session 取得 provider／channel／user ID，不能相信請求內的身分欄位。每次兌換在 D1 取得**一個 UTC 判定時刻**，同一交易確認碼驗證值匹配、綁定的商店／LINE 身分／顧客紀錄識別／資格世代符合、顧客仍待核准、碼為未使用且未作廢／取代，以及判定時刻**早於**到期時間；等於到期時間即失效。所有條件成功才在同一交易消耗碼、授予購買資格、記錄兌換結果和時間；任何一項失敗都不能只核准或只消耗碼。
- 拒絕或撤銷在自己的 D1 交易中改資格、推進資格世代並使未用舊碼不可兌換；撤銷還按[既定權限規則](04-buyer-approval.md)禁止新購物車操作、清空購物車，但保留舊訂單的查看及付款回報。拒絕／撤銷先提交則稍後兌換失敗；兌換先提交則稍後撤銷成為目前狀態。人工重新開通也推進世代，不讓較早核發的碼因顧客再次變成待核准而復活。待核准帳號刪除、LINE 身分轉綁與舊身分失效也須在同一 D1 交易使其未用碼失效；重新登入建立**新且不重用**的顧客紀錄識別，舊碼即使尚留作清理／稽核，也不能綁到新紀錄。結帳仍在自身 D1 交易檢查當下資格，不以曾兌換成功的畫面或舊 session 授權。[結帳一致性](07-checkout-consistency.md)、[顧客資料生命週期](09-customer-data.md)
- D1 `batch()` 的 SQL 陳述式報錯可回滾交易，但條件更新影響零列不會自動報錯；實作須用資料庫約束或同交易斷言，讓缺少任何預期的碼／顧客轉換使整筆交易失敗，並在真實 D1 驗證同時兌換、兌換對撤銷與補發的競爭。不能先讀狀態再分開寫入兩個請求。[Cloudflare D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

### 重送、失敗與保存

- 同一已綁定顧客重送已成功消耗的碼，在兌換結果仍依[資料期限](09-customer-data.md)保存時，只讀取原結果與**目前**資格，不再寫入核准；目前已撤銷時清楚顯示不可購買。原結果屆滿刪除後，只能顯示目前資格及通用的舊碼失效結果，不承諾重建已清除的歷史。其他身分、錯碼、過期或已作廢碼都不改狀態，顧客只看「此碼無法使用」和自己的申請狀態，避免透露他人身分或碼是否存在；管理員在受保護後台可查核發／作廢／兌換原因。限制錯碼嘗試頻率，碼本身須難以猜測。
- 網路逾時或 D1 結果不明時，先以原請求及當前身分查權威 D1 結果；仍不明則顯示暫時無法確認，不宣稱已核准，也不在客戶端產生資格。D1 不可用／額度耗盡時暫停核發、補發、作廢、兌換與資格變更，待恢復後查原結果再重試。清理排程晚到不能延長碼的 168 小時有效期。
- 未兌換碼到期後 30 天清理；已兌換結果及必要管理操作依相關訂單結案後 1 年或獨立操作後 1 年的規則保留可識別連結，詳見[顧客資料生命週期](09-customer-data.md)。備份還原須重播碼消耗、補發／作廢與資格撤銷；無法確認備份後權威結果時關閉兌換與結帳，不能讓舊備份復活邀請或購買資格。[獨立部署票](08-repeatable-deployment.md)

驗收至少覆蓋：同碼並發兌換、同碼另一 LINE 身分輸入、到期當刻、錯碼猜測、補發對舊碼兌換、兩名管理員同時補發、核發後回應遺失、兌換後回應遺失、拒絕／撤銷與兌換兩種提交順序、撤銷後重送舊成功碼、原兌換紀錄屆滿後重送、人工重新開通後重送舊碼、待核准帳號刪除再登入與舊碼競爭、LINE 轉綁與舊碼競爭、管理員撤權對核發／補發／作廢三種競爭、管理員自發碼、D1 故障、清理延遲與備份還原。每例檢查僅一組有效碼、核准狀態、購物車、舊訂單權限及操作紀錄。
